# Traj2Language 分层协作与交付规程

> **用途：** 规定 v0.8 从 ③ 单段原型起，执行指令怎样写、交给谁、怎样验收。它是《AI 分层协作研发与可验证交付工作框架 v1.0》（编号 AICD-FW-001，下称"原框架"）在本项目里的精简落地版。
> **优先级：** Project Instructions 高于本规程，本规程高于原框架。P0–P3 的定义、停止条件、冻结规则和命名一律以 Project Instructions 和命名规范为准，本规程不另作定义。原框架只作参考，不作执行依据。
> **生效：** 2026-11-01 起，用于 V8-03 及之后的工作项。V8-01、V8-02 不受影响。
> **本地副本：** `F:\CASIA\Drone Swarm Situational Awareness Algorithm\traj2language_docs\00_分层协作与交付规程.md`。原框架原文存放在 `traj2language_docs\参考\协作框架\`。

## 1. 角色

| 角色 | 由谁担任 | 做什么 | 不做什么 |
|---|---|---|---|
| 负责人 | 用户 | 批准每个里程碑的工作项清单；批准里程碑完成；决定设计变更；选择执行工具和模型；在本地运行需要本地数据的复跑；转交指令与结果 | 不逐个审批工作项 |
| 规划审查方 | 助手（本 Project 中的对话） | 写设计与执行指令，包括预置测试；下发前核对真实仓库；为每个工作项标注建议执行模型；审查代码与证据；在云端克隆中复跑不依赖本地数据的测试；维护台账和登记表 | 不凭记忆写路径和接口；不替负责人做设计变更；不管执行工具怎样配置 |
| 实现方 | 负责人在本地打开的编码工具（Claude Code、DeepSeek Harness、Codex 等）及其模型 | 按指令实现并推送审查分支 | 不修改预置测试、判据和冻结产物；不推 `main`；不强制推送 |

**指令与执行工具无关。** 同一份指令交给任何实现方都一样执行，不为某个工具或模型写不同版本，也不写工具的安装、接入或操作步骤。指令开头只多一行"建议执行模型"（第 2 节）。

## 2. 建议执行模型

规划审查方按工作项难度给出建议，负责人可以不采纳。

| 类别 | 例子 | 建议执行模型 |
|---|---|---|
| 核心算法 | 运动生成、任务切换、时序求解、窗口版判据、段核验、标签与过渡区间的定义性部分、划分、防捷径探针 | 强模型（如 Claude） |
| 验证与标定 | 离线核对、仿真器标定、阈值测量、可行性检查、诊断 | 强模型 |
| 管道与工具 | 读写与格式转换、加载器、拼接与连续性检查、配额计数、统计报表、可视化、测试脚手架、规范清楚的纯函数 | 低价模型（如 DeepSeek） |

**判断标准：** 指令里的规范能否写得比实现更短，且能否用有独立预期的测试完全覆盖。两条都满足，才建议低价模型。这类工作项尽量小：新增代码大约几百行以内，全部测试一分钟内跑完。

写法：指令开头一行 `建议执行模型：低价模型（DeepSeek 即可）——理由一句话` 或 `建议执行模型：强模型（Claude）——理由一句话`。

**验证与标定类工作项的验收方式不同：** 交付的是测量结果和结论，验收看三件事：测量协议是否完整执行，原始数据是否齐全，结论是否与数据一致。测出来的数值不好，不算实现失败；只有当数值本身就是某条 P0 判据时，才按 P0 处理。

## 3. 一次性准备

1. **（可选）在 GitHub 上保护 `main`：** 禁止强制推送和直接推送。只有账户支持时才做。
2. 工作目录、分支和 Python 环境由每份指令写明，所有实现方相同。所有冻结工作树共用同一个 git 仓库，指令一律只允许在开发工作树和指定的审查分支上操作，禁止改动其他工作树和分支（保护冻结代码与数据的可复现性）。

## 4. 工作项的流转

```
草稿 ──下发前自查通过──▶ 已下发 ──实现方推送──▶ 待审查 ──▶ 已接受
                                                    ├──▶ 返工（出 V8-xxb 指令，回到"已下发"）
                                                    └──▶ 阻塞（交负责人）
已接受 ──上游改动──▶ 失效待复核 ──复核──▶ 已接受 / 返工
```

- 状态记在命名规范第 5 节的登记表"状态"列，由规划审查方更新。台账 #7 只写当前进行到哪个工作项。
- **里程碑开始时：** 规划审查方在对话中给出本里程碑的工作项清单，包括每项的名称、类别、建议执行模型和先后顺序。负责人批准后，清单写进台账 #7 的"下一步"。编号在写指令时才分配，不预留。
- **下发：** 清单内的工作项通过第 5 节自查后，直接下发，不再逐个审批。清单外新增工作项需要负责人同意。
- **分部分：** 一个工作项可以分成几部分。每部分单独提交、单独跑预置测试；某部分不通过，只停依赖它的后续部分。审查意见按部分给结论，未通过的部分单独返工。部分用"第 n 部分"称呼，不另编代号。
- **接受之后：** 由下一份指令的第一步把审查分支合并进 `dev/v0.8`（不强制推送）。

## 5. 下发前自查

规划审查方逐条确认，并把结果写在指令末尾的"自查"一节，每条一行。

1. 该工作项在已批准的清单内，或已得到负责人当次同意。
2. 已核对真实仓库：基于哪条分支、哪个提交；要调用的函数，其签名已从代码中核对，或引用的是最近一份报告中的已证事实。
3. 每条约束可行，口径唯一（Project Instructions 第五节、第八节）。
4. 预置测试已写全，每条断言都注明了独立预期的来源（第 6 节）。
5. 写明了允许修改的文件，以及不得修改的范围。
6. 停止条件只列 P0。昂贵步骤之前设了快速检查点。每一步都有耗时预估。
7. 开头如实写明项目性质（Project Instructions 第九节）。
8. 指令里贴出了实现方要调用的接口原文（签名和文档字符串），不能只给文件路径。
9. 指令不含任何特定工具或模型的操作步骤；开头已标注建议执行模型。

## 6. 预置测试

- **谁写：** 规划审查方在指令中写出完整的测试代码。实现方原样放入 `tests/v08/<工作项>/`，文件名以 `test_preset_` 开头。
- **独立预期的来源只限以下几种：** 手算或解析解；小规模穷举；数学性质，例如不变量、对称性、单调性、平移不变性；v0.7 冻结代码的输出（作回归基准）；已有报告中的实测事实，例如 V8-01 的续跑误差 4.4 mm。**不允许**先运行待测代码，再把它的输出抄成断言。
- **容差：** 每个容差都要写明来源，例如仿真步长、测量精度或 V8-01 的实测值。
- **实现方不得修改或删除预置测试。** 它可以另加自己的测试。如果它认为某条预置测试本身有错：
  - 该项停下，不改测试；
  - 在报告的"疑似预期错误"中写明理由，最好附手算过程；
  - 其余各项继续做。
- **审查时的核对：** 规划审查方在云端克隆中逐字比对预置测试（核对 SHA256 与 `git diff`），发现被改动的，一律退回。这条保护的是"评估方式错误"这项 P0：被改过的测试不再能证明任何东西。它不依赖执行工具有没有只读开关。

## 7. 证据等级

| 等级 | 含义 |
|---|---|
| 口述 | 只有"已完成"之类的说明 |
| 可读 | 代码已推送到审查分支，可以静态阅读 |
| 有记录 | 另附运行记录：命令、提交号、环境版本，以及每项测试的结果（通过、失败或未运行）和完整输出 |
| 已复跑 | 实现方以外的一方，在同一提交上复跑，得到相同的结论 |

- **默认要求：** 接受一个工作项，至少要达到"有记录"。没跑过的测试必须写"未运行"，不能写成通过。
- **以下工作项必须"已复跑"：** 涉及标签、核验结论或过渡区间的计算；涉及划分或学习视图（防泄漏）；涉及间距、禁区等物理有效性检查；涉及防捷径检查；涉及任何 val 或 test 评估。也就是直接保护 P0 的工作项。
- **由谁复跑：**
  - 不依赖本地数据的测试，由规划审查方在云端克隆中复跑。云端的包版本和 `llm` 环境不同，所以只比较"测试断言是否全部通过"，不比较数值是否逐位相同，以免重演 FT1 那次因求和顺序不同而误停。
  - 依赖本地数据或 Windows 环境的，由负责人运行报告里给出的一条复跑命令，再把输出推送上来或贴回对话。

## 8. 审查结论与返工

审查意见写成 `claude/v08/<工作项>_审查意见_<日期>.md`，结论只有三种：

| 结论 | 条件 | 后续 |
|---|---|---|
| 接受 | 预置测试未被改动且全部通过；未触碰禁止范围；证据等级达到要求；没有未处理的 P0 | 由下一份指令合并 |
| 返工 | 实现没有满足指令，或者指令本身有错 | 出 `V8-xxb` 指令，只列需要改的地方。指令本身有错时，在审查意见里写明"指令修订"和原因 |
| 阻塞 | 某个前提不成立（例如成员动力学独立性核对未通过），或需要改动设计 | 停下，交负责人决定。改动设计时，结论记入决策文档 |

- **问题分级：** 审查意见里的每个问题都标 P0–P3（以 Project Instructions 为准）。只有 P0 能导致"返工"或"阻塞"；P2、P3 只记录。
- **设计变更：** 只要涉及判据、标签定义、划分、冻结产物，或 V8-02 中定义性的内容，就属于设计变更，必须由负责人决定。返工指令不得夹带设计变更。
- **返工上限：** 同一工作项返工两轮（到 `V8-xxc`）仍未接受，不再出下一轮返工。规划审查方先重新审视指令本身是否可行，必要时建议改用强模型，并在对话中向负责人说明。这是为了避免一条一条地打补丁（Project Instructions 第三节）。

## 9. 失效待复核

- **触发：** V8-02 修订；相关决策改变；已接受的上游工作项因返工改了接口或数值。
- **做法：** 规划审查方列出受影响、且已接受的工作项，标为"失效待复核"，逐项写明要复核什么。复核优先用最便宜的办法：先在新的上游上重跑这些工作项的预置测试，测试失败了再做针对性审查。不默认整项重做。
- 只有影响 P0 的失效才阻塞下游；其余边做边复核。

## 10. 文件约定

| 文件 | 位置 | 内容 |
|---|---|---|
| 执行指令 | `claude/v08/<工作项>_<标题>_<日期>.md`；本地指令包在 `_handoff\<日期>_<工作项>_<英文短名>\` | 沿用 V8-01 的格式：项目性质、命名、目的、开工前复述、预计耗时；规则（不得修改、输出位置、停止条件、只报事实）；正文；回报与提交。在此基础上补四块：**建议执行模型**（写在开头）、**允许修改的范围**、**预置测试**（附每条断言的预期来源）、**接口原文** |
| 执行方报告 | 生成器仓库 `docs/v08/<工作项>/REPORT.md` | 依次写：复述；每项结论；分支、基于的提交与推送后的提交（用 `git ls-remote` 核对）；改动文件清单（附 `git diff --stat`）及是否触碰禁止范围；预置测试逐项结果、命令与完整输出位置；自加的测试；偏离指令之处及原因；疑似预期错误；一条复跑命令；环境版本；实际使用的模型；最后单列"执行方观察"，与事实分开 |
| 审查意见 | `claude/v08/<工作项>_审查意见_<日期>.md` | 依次写：结论与达到的证据等级；核对结果（预置测试未改、禁止范围未碰、各项 P0）；问题清单（分级、位置、要求）；是否属于指令修订或设计变更；下一步 |

不另设管理目录、机器可读记录和独立的交接文件。
