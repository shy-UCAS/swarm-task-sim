## 1. 依据

**V8-13c 全量的分项 CPU 时间：**

| 环节 | CPU 时间 | 占比 |
|---|---|---|
| 跟踪仿真 | 12,139 s | **63%** |
| 优化 | 4,596 s | 24% |
| 骨架 | 1,824 s | 9% |
| 核验 | 779 s | 4% |

- 仿真耗时与"飞行时长 × 人数"的相关系数为 0.96，约每架飞机每飞 1000 s 耗时 6 s。
- 8 进程的并行效率约 66%：同族合同排在同一进程里顺序跑，造成负载不均。

**冻结动力学核心本身就是多机向量化的：**
- `SynchronousEngine`、`VelocityController`、`PointMassJerkPlant` 的状态都是 (N, 3) 数组，按行运算（`norm(axis=1)` 等）；
- 现在的 `run_tracking_segment` 逐成员各建一个 N = 1 的引擎，每 20 ms 一步、每架飞机一次 Python 调用。

**规划审查方云端实测**（`InjectableEngine`，8 架飞机，5000 步，含状态反馈的闭环）：同一引擎批量运行与逐机运行**逐位相同**（`np.array_equal`，样本与终态都相同）；引擎部分耗时 5.72 s → 0.75 s，**快 7.6 倍**。

## 3. 实现

### 3.1 新文件 `v08/sim/tracking_batch.py`

不修改 `v08/sim/tracking.py` 及 `v08/sim/` 中已有的文件。

```python
def run_tracking_group(references, states, *, final=True, guidance=None, sim=None, use_precomputed_reference=None)
    -> list[MemberSegmentResult]   # 与输入成员顺序一致，每个元素与 run_tracking_segment 的返回同构
```

**算法：** 与 `run_tracking_segment` 逐行对应，只把"每成员一个引擎"改成"一个编组一个引擎"。

1. 对每个成员调用 `tracking._check`，口径相同。所有成员的 `tau_us` 都必须是 0（第 0 段，统一时钟）。
2. 建一个 `InjectableEngine(cfg, PlantState(P0[N,3], V0[N,3], A0[N,3]), None, 0)`，行顺序就是输入顺序。
3. 每个成员各自记录：`release_us`、`T_i`、`budget_us_i`、`hold_us`、`holding_i`、`hold_end_i`、`done_i`、`status_i`、`end_us_i`、`end_state_i`。公式与 `run_tracking_segment` 相同。
4. 循环条件：`engine.time_us < max_i(budget_us_i)` 且还有成员未结束。每步：
   - **(a) 判定结束：** 对每个未结束的成员，依次判断：
     - 若 `holding_i` 且 `t >= hold_end_i`：结束，`status = "ok"`，`end_us_i = t`，`end_state_i` 取当前 `engine.state` 第 i 行的拷贝；
     - 否则若 `t >= budget_us_i`：结束，`status = "sim_timeout"`，`end_us_i = t`，终态同样取拷贝。
     
     这与单机循环在 `while engine.time_us < budget_us` 处退出等价。所有成员都结束就跳出循环。
   - **(b) 参考值：** 每个成员在 `t_abs = t/1e6` 处的 p_ref、v_ref、a_ref，取法见 3.2。
   - **(c) 开始保持的判定：** 逐成员用 `math.hypot`，与 `tracking.py` 完全相同的表达式和比较。不得改用 `np.hypot`，因为它决定保持从哪一步开始，进而决定轨迹长度。
   - **(d) 期望速度：** 用 NumPy 逐元素计算 `u0 = v0 + tau*a0 + k*(p0 - x0)`，以及对应的 `u1`、`u2`，运算顺序与 `_command` 相同。已结束的成员也照常计算，结果不输出。
   - **(e)** `engine.step(U)`。
   - **(f)** 逐步诊断量（位置误差、速度误差、jerk、加速度）按成员向量化记录，只记到该成员结束为止。
5. **成员 i 的输出：**
   - `engine.samples` 中 `t_us < end_us_i` 的帧，取第 i 行；
   - `TrackingRecord` 各字段的口径与单机版相同；`wall_s` 记为编组总耗时除以成员数，并标注是均摊值；
   - 状态、时间轴构造与单机版相同。

### 3.2 参考值的取法

- **预计算：** 对每个成员，在 20 ms 步网格上，用同一个 `reference.pva` 一次性对时间数组求值。
- **使用前必须核验：** 对每个成员，预计算结果须与逐点标量调用 `_pva(reference, t)` 的结果 `np.array_equal`，网格全长都要比。
- 核验通过才用预计算；不通过则在循环内逐成员调用标量 `_pva`。这样仍是逐位一致，只是慢一些。
- 报告中写明实际采用了哪一种，以及两种做法的耗时。

### 3.3 运行器切换

`joint_monitoring.py` 中每成员调用 `run_tracking_segment` 的地方，改为每个编组调用一次 `run_tracking_group`。后续的 `stitch`、`verify_segments`、`check_validity` 不变。`run_tracking_segment` 保留，供测试与对照使用。

### 3.4 调度（负载均衡）

1. 派发 worker 之前，用单进程把 40 族的场景上下文与距离场缓存全部建好。之后 worker 对缓存**只读**，消除并发写，也就不再需要"同族合同排在同一进程"。
2. 200 个合同和 100 个多样性种子一律以单个任务派发：按预计成本降序排列（预计成本取"第 0 编组人数 × 地图边长"），动态分配，chunksize = 1。
3. 输出按业务键写入，与派发顺序、进程数无关。5 个合同的单进程复跑须与 8 进程输出逐字节一致，沿用原要求。
