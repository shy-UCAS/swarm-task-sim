## 1. 使用方法与职责

每轮只执行一个阶段，流程固定为：

1. 用户发送“通用执行指令 + 本阶段指令”；首次只发送 M2-00。
2. DeepSeek 实现、运行必要验证、汇总实际结果，状态写为 `AWAITING_REVIEW`，停止。
3. 用户将本文末尾的审阅指令交给 Codex。Codex 核对代码差异、测试与原始证据，必要时独立复跑，不能只相信执行总结。
4. Codex 给出 `PASS`、`FIX_REQUIRED` 或 `BLOCKED`。只有 `PASS` 且用户明确发送下一阶段指令，才推进下一阶段。
5. `FIX_REQUIRED` 时只修当前阶段；保留旧失败结果，以新 attempt 输出修复结果，然后再次停止审阅。`BLOCKED` 时明确缺少什么输入或决定，不能把缺失项填成已完成。

DeepSeek 负责限定范围内的实现与举证；Codex 负责检查设计与实现是否一致、语义是否正确、证据是否足以放行；用户决定开始哪一轮。这里的“审阅”默认不授权审阅者直接修改业务代码，修复内容先转成明确指令。

这套流程适合能力较弱、成本较低的执行模型，但不能保证仅凭遵循提示词就正确。尤其是连续跟踪、事件时刻和巡逻语义，必须检查独立可计算的反例。

### 2.1 正确理解覆盖矩阵

三意图四飞法是四个合法意图—飞法组合，并非三意图任意交叉四飞法：

| 意图 | 飞法 | 机数 | 最少正例 | 最少配对负例 |
| --- | --- | --- | --- | --- |
| reconnaissance | equal_strip_lawnmower | 2 / 3 / 4 | 每种机数 1 个真实任务 | 每个正例配 1 个状态改变产生的失败执行 |
| reconnaissance | equal_strip_rectangular_spiral | 2 / 3 / 4 | 同上 | 同上 |
| patrol | staggered_same_loop | 2 / 3 / 4 | 同上 | 同上 |
| rapid_passage | line_abreast | 2 / 3 / 4 | 同上 | 同上 |

因此基本矩阵为 **12 个合法组合、至少 12 个任务输入、24 次正/负执行**；额外边界测试、数值收敛和性能重复不替代这些单元。以上飞法名已对照当前 `registry.py`；M2-02 再核对执行版本并登记进矩阵，不能凭名称猜测。

“真实任务”指既有任务源中的有效 TaskSpec，记录来源路径与原始哈希；新构造任务只能作补充边界用例。不得只删减飞机、改任务名，就宣称满足真实 2/3/4 机任务覆盖。若开发池缺某单元，先报告缺口，待审阅决定补充来源，不能借用盲测任务。

正例要求实际 `mission_success=true`；配对负例要求实际 `mission_success=false`，且能定位失败条件和对应轨迹。`null` 是未知，不计入失败例。质量不合格、引擎崩溃也不能替代语义负例。基本矩阵中的正例和负例均应通过公共产物完整性/质量检查；若现有定义不允许某类失败样本质量合格，先说明契约冲突，不能自行放宽规则。

负例沿用同一 TaskSpec，以显式、可复现的执行配置或经审阅的测试故障改变实际飞行状态，再重新经过完整数据链。优先复用已有能力/响应参数；若必须新增故障注入，单独说明版本、配置、作用时段及实际响应。禁止直接改轨迹文件、标签、判定阈值，禁止在生产控制器里按意图偷偷改变动力学。

```text
1. 从 M0 来源索引确认 T1/T4 的 14 个 family 全部是 development_reference。

   分别登记为开发/排除/待核实，不能悄悄作为盲测。
3. 冻结候选 roster：来源路径、family、规范 scene 哈希、重复关联、使用史、排除原因。
   同 family 必须同组；预先约定的近重复关联作为连通分量一起分组，不能跨组泄漏。
   写明近重复检测规则及未能保证的范围，不能宣称只做精确哈希就排除了所有近重复。
4. 在运行候选结果之前登记划分方法与种子。建议采用本指南默认：
   seed=2026101202；分量内 family ID 去重并按 Unicode 码点排序，以无多余空白、
   ensure_ascii=true 的 JSON 数组序列化，取 UTF-8 字节的 SHA256 十六进制为 component_id；
   按 SHA256(UTF-8('2026101202|' + component_id)) 排序；并列按 component_id；
   前 floor(G/2) 个分量为 calibration，其余为 blind_holdout，G 是可用分量数。
   写清哈希与排序实现，并用小型固定输入证明可复算。分量大小不同可能导致 family 数不等半，
   报告实际数量，不为“更均衡/更好结果”反复换种子。G<2 时不能声称完成有效划分。
5. 写 evaluation_split.json、完整候选与排除清单的哈希、算法/种子、分组结果和冻结说明。
   M2 不读取 calibration/blind_holdout 的轨迹、标签、描述或运行结果来开发。
   blind_holdout 保留给未来独立验收；M3 调参只能用 calibration 及已登记开发资料。
   若未来开盲后改模型，该集合降为开发，必须另找最终测试；不能还称盲测。
6. 从已知开发来源登记 12 个真实任务，填全四合法飞法×2/3/4机，固定原始 TaskSpec 哈希。
   逐项登记返航、错峰、阶段类型、航点数、巡逻圈数、是否窄条带等特征。
   不改源任务以凑格；缺真实任务时明确 BLOCKED，不动保留集补洞。
7. 登记每个正例的负例构造方法、预期失败条件及待验证字段；此时 actual_result 为 null，
   不能把预期写成实测。额外合成边界任务单列，不计入真实矩阵。
8. 输出来源清单、小型划分 JSON、初始覆盖矩阵与报告，停止等审阅。
```

**放行标准：** 留出候选、排除理由、稳定算法与种子可复算；集合交集为零；任务源满足 12 个单元且不动留出结果。若来源缺失或使用史无法确认，审阅者先处理数据缺口，不能直接批准控制器开发后再补登记。
