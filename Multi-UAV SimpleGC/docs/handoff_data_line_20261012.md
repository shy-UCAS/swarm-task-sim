## 7. fastsim（当前主线）

### 7.1 计划

依据：`fast_dynamics_engine_implementation_plan.md`（另一助手融合 Claude 原计划后的修订版 r2，位于仓库 docs）。阶段划分：
- **M0：** 摸底、契约设计、来源索引；
- **M1：** 内核，以及一个最小任务的端到端数据链；
- **M2：** 三意图四飞法、2/3/4 机、多航点、返航和时序；
- **M3：** 用 SITL 数据做确定性校准；
- **M4：** 扰动与噪声、两种输出模式、小规模试产；
- **M5：** 用未见过的 family 做独立验收。

计划估算 12–20 人日。**按原则四，只推进当前阶段，不提前搭建升级接口。**

### 7.2 M0/M1 结果（已通过审查）

- 质点模型（位置、速度、加速度），受限加速度和加加速度，常 jerk 多项式积分；内部步长 0.02 s，整数微秒时钟，多机同步更新；
- 输出为 10 Hz 半开网格 [0, T)，帧数为 ⌈10T⌉；
- 已打通一个两机快速通过任务（T1 的 `rapid_passage_0000_v00`）的完整链路：仿真 → 分析 → 导出 → 审计 → 事实与描述 → 加载；
- 新协议明确标注引擎真值、合成观测、`sim_clock`，固件为"不适用"，没有伪造 SITL 证据；
- 负例由飞行状态改变产生：低速穿越 → 任务失败；超时 → 结果未知；
- 测试 406/406 通过；DR130 金标准 260/260；v0.5 示例加载 4/4；
- 步长减半：位置差 p99 约 1.5 cm，事件时间差最大约 5 ms；
- 性能：
  - 内核约 280 倍实时（2 到 16 机）；
  - **全流程单条约 1.8 秒，单进程每小时约 2000 条**（仅限这个短任务）；
  - 结论：分析环节不是瓶颈，SITL 慢主要慢在飞控日志解析和时钟对齐；
- 新样本一律 `training_eligible=false`。

### 7.4 M2 汇报的复核要点

- 每种意图、飞法、机数的组合是否都有正例和负例；负例是否确实由飞行状态改变产生；
- 连续转弯是否满足约束，过点时是否没有错误地悬停；覆盖率、重访间隔、圈数的判定是否正确；
- 多机错峰出发和阶段释放是否按仿真秒执行；
- 不同 worker 数和派发顺序下结果是否一致；SITL 老路径回归是否通过；
- 输出是否已移到 `SwarmData`；代码是否已在本地分支提交；
- 各类任务的单条耗时（巡逻那种 4 机、几分钟的任务会比 M1 的短任务慢）；

## 8. 算法线相关（另一对话负责，仅供参考）

- 用户复现了几篇同类意图识别方法作为对照，发现与自己的方法在意图分类准确率上很难拉开差距。很可能的原因是：用完整轨迹分类意图，这个任务太简单了；
- 上一对话给过的建议：
  - 先做"难度探针"：手工特征（时长、直线度、累计转向角、区内停留时间）配逻辑回归或决策树；
  - 主要评测改为**早期识别**：只看前 10%、20%……的轨迹；
  - 用固定时间窗或按观测比例截断，消除**时长捷径**（快速通过飞得短，巡逻飞得长）；
  - 离线加噪做鲁棒性测试；
- 用户决定系统设两路正式输出：意图分类的结构化结果（权威输出），以及语言描述（两路互相核对，分类结果不输入语言分支）。

## 9. 上一对话的经验教训（请延续）

1. **先确认阈值可行，再定标准**（原则五第 2 条）。Claude 在这方面犯过两次错：
   - 定"速度尺度 ≤0.5%"之前，没有验证测量方法本身的精度；
   - 缩短固件等待之前，没有查清这段等待还承担着"等待参数表就绪"的作用。
2. **每条门禁都要说清它保护的是哪项研究结果。** 说不清的应降级或删除：
   - 时钟残差 0.05 秒、机间距 5 米整批停止，都定得过严，已放宽；
   - 而 family 三意图完整、时间轴存在、双通道判定、模板划分这些必须守住。
3. **"一次意外就整批作废"的设计代价太大。** 环境类异常应该是"暂停待查"；只有确认违规才不可恢复。
4. **防泄漏：** 用于校准和调参的数据不能再当盲测（例如 T1/T4 与 r2 是同一批任务）。
5. **执行方的报告要独立核验：** 关键结论要求附证据位置；以远端 CI 为准；关键节点请 Opus 做独立审查（之前的审查发现了 7 项 P2，没有 P0）。
