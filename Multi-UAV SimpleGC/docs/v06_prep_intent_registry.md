# v0.6 准备步骤 2：意图模块化（给执行方的指令）

> **适用仓库：** `Simulation-dev`（只在这里改动）
> **前置条件：** 分片并行"暂停 1"的汇报已经用户确认。在同一个本地工具会话中进行。
> **范围：** 把现有的侦察、巡逻两种意图迁入"意图注册表"；"快速通过"只做纸面核对，不写实现。场景层面的扩展（被保护目标等）、新意图的实现、第二种飞法的实现，都不在本次范围内。
> **依据：** 用户已确认两点：① "快速通过"的定义（见第 5 节）；② 注册表从一开始就支持"同一意图多种飞法"（见第 3 节）。

## 0. 约束

1. 老仓库归档（`Simulation`，提交 `8eaf583b`）**只读**。可以读取其中的 v0.5 数据做对照，所有输出一律写到 `SIM_DATA_ROOT` 下。
2. **这是纯重构。** v0.5 两种意图的参数采样、规划、验证、事实提取、描述生成，行为一律不变。不借机"顺手修"任何逻辑；发现的问题写进汇报。
3. 不要过度设计：不做插件自动发现，不做配置描述语言，不搭多层抽象基类。注册表就是一个显式字典，在一个文件里逐行登记。
4. 分片并行的入口改为通过注册表调用意图；分片并行原有的测试必须继续通过。
5. 本步骤不跑仿真。
6. 停止条件只有第 7 节所列；其他异常写进汇报后继续。

## 1. 先做一轮只读摸底（不改代码）

逐项给出结论，并附文件路径和行号：

1. 侦察、巡逻目前的参数采样、规划、验证、可见事实提取、描述模板，各自位于哪里。
2. 速度、机数、起点/进场方向等**共用参数**，两种意图是否走同一段采样代码、同一个分布。如果不是，标出差异（这可能是 v0.5 的分类捷径；只上报，不修改）。
3. 验证器和可见事实提取目前的输入中，是否包含规划结果（航点、阶段、规划时长等）。如果有，标出每一处用途。
4. 生成任务清单时，随机数的抽取顺序（用来保证重构后种子不变）。
5. 任务的结束方式：是否所有任务都默认返航或在起点降落；轨迹记录在什么时刻截止。（供第 5 节的纸面核对使用）

摸底完成后直接继续，不需要暂停。如果第 3 项发现验证器或事实提取离开规划结果就得不出现在的结果，按第 7 节停止。

## 2. 意图包与注册表

一个意图包包含 5 个组件。下面的名称和类型仅为示意，执行方可以按现有代码调整，但**输入限制不能改**：

```python
@dataclass(frozen=True)
class Style:                      # 一种飞法
    name: str                     # 描述性名称，如 "lawnmower"
    version: str
    plan: Callable[[MissionSpec], Plan]

@dataclass(frozen=True)
class IntentPack:
    name: str
    sample_params: Callable[[Rng, SharedParams], IntentParams]  # 只采样本意图特有的参数
    styles: dict[str, Style]                                     # 至少一种
    verify: Callable[[Trajectory, MissionSpec], VerifyResult]
    verifier_version: str
    extract_facts: Callable[[Trajectory, MissionSpec], Facts]
    facts_version: str
    templates: TemplateSet        # 训练组、测试组、版本号

REGISTRY = {
    "recon":  RECON_PACK,
    "patrol": PATROL_PACK,
}
```

规则：

- **共用参数由框架采样**，意图包不得重新定义速度、机数、进场方向等共用参数的取值。如果摸底第 2 项发现 v0.5 存在意图专属的分布，本次照原样保留（为了保证等价），在汇报中标出，留到 v0.6 正式内容中统一。
- `MissionSpec` 只包含"任务说明"：区域几何、共用参数、本意图参数、是否要求返航等。**不包含任何规划结果。**
- 验证器和事实提取的输入，只有轨迹和 `MissionSpec`。

---

## 3. 多种飞法（对应用户确认 ②）

- 每个意图包至少登记一种飞法。v0.5 的侦察、巡逻各登记一种，用现有飞法的描述性名称命名。
- 任务清单中的每个任务都记录：意图、飞法，以及四个组件的版本号（规划器版本即飞法版本、验证器、事实提取、描述模板）。
- 飞法在冻结清单时由清单生成器决定：
  - **只有一种飞法的意图，不得消耗随机数**（否则 v0.5 的种子序列会变）；
  - 有多种飞法时，用独立的随机子流抽取，不影响其他参数的抽取。
- 飞法只作为元数据导出，不放进模型输入字段。
- **验证器不得按飞法分支。** 同一意图无论怎么飞，"任务是否完成"的判据都相同，否则同一个意图标签在不同样本中含义不同。

---

## 4. 由框架强制执行的规则

1. **验证器和事实提取不引用规划结果。** 这条保护的是：标签和描述反映的是"观察到的"，而不是"计划要做的"。
   - 函数签名只接收轨迹和 `MissionSpec`；
   - 静态测试：这两个模块（包括它们的导入链）不导入规划器模块；
   - 行为测试：让规划器在被调用时直接报错，再在样本轨迹上运行验证器和事实提取，结果不变。
2. **注册时检查：** 每个意图包的组件齐全、版本号非空；训练模板组和测试模板组都不为空，且两组之间没有相同的句式（保护模板划分不泄漏）。
3. **共用参数对比表（诊断项，不阻塞）：** 清单冻结后自动输出一张表，对比各意图的速度、机数、进场方向和预计时长分布。共用参数是否同源，由第 2 节的结构保证，不靠这张表判定。预计时长不同（巡逻比侦察长约 80 秒）是已知情况，留给 v0.6 正式内容处理。

---

## 5. "快速通过"纸面核对（对应用户确认 ①）

**已确认的定义：** 从区域一侧进入，路径直接穿过区域，从另一侧离开；不停留、不绕圈；速度与其他意图共用同一套取值，不用更快的速度来体现"快速"。

只写一份不超过一页的核对说明，放在 `docs/` 下，**不写实现代码**。逐项回答：

1. 五个组件各自需要做什么（每项一两句）。验证器的判据只列名称（例如：进入区域、从对侧离开、区域内无停留、无绕圈），**不定阈值**，阈值等有轨迹数据后再定。
2. 新增它是否只需要：一个新的意图包、注册表一行、描述模板。如果需要改框架，列出改哪里、为什么。
3. 重点核对：
   - 任务如何结束：离开区域后飞机去哪里、在哪里降落、轨迹记录截止在什么时刻；
   - "是否返航"这个槽位对它的含义是否和其他意图一致；
   - 进入侧和离开侧能否由共用的进场采样决定。
4. 列出它可能带来的捷径风险（例如总时长明显短于其他意图），只列出，不处理。

## 6. 测试

1. **规划等价性：** 分别用重构前的代码（当前 dev 提交）和重构后的代码，以 v0.5 的主种子生成完整任务清单和规划结果，逐任务比较规范化 JSON 的哈希，必须完全一致。比较时排除本次新增的飞法和版本号字段。金标准以哈希列表的形式存为测试夹具（小于 5 MB），可以进 CI。
2. **标签与描述等价性（本地测试，不进 CI）：** 在归档的 260 次运行轨迹上（只读），分别用重构前后的代码计算任务成功、槽位标签和描述文本，三者必须完全一致，并且与归档中已记录的结果一致。汇报中写明比较的运行数和描述条数。
3. **不引用规划器：** 第 4 节第 1 条中的静态测试和行为测试。
4. **随机数隔离：** 测试中临时给侦察加一种假的第二种飞法，所有任务的种子、family、划分和共用参数都不变，只有飞法字段不同；去掉后与 v0.5 清单完全一致。
5. **注册检查：** 缺组件、版本号为空、训练组与测试组模板重叠，三种情况都会被拒绝。
6. 分片并行的全部测试继续通过，并确认分片执行路径确实经由注册表调用意图。
7. 本次改动涉及的模块，如果原有的单元测试不依赖数据，纳入 CI。

## 7. 停止条件（只列 P0）

1. 归档目录有任何改动。
2. **重构前后结果不一致**（第 6 节第 1、2 项）：说明重构改变了行为。只花一轮定位原因，然后停下汇报。不得通过修改金标准或放宽比较来让测试通过。
3. **重构前的代码与归档记录不一致**（第 6 节第 2 项的后半部分）：说明冻结数据无法由其自身代码复现。只花一轮定位原因，然后停下汇报。
4. 摸底发现验证器或事实提取必须依赖规划结果才能得出现有结果：意味着 v0.5 的标签或描述可能报告的是"计划"而不是"观察"。停下汇报。
5. 注册检查发现 v0.5 的训练模板组与测试模板组存在重叠：停下汇报。

其他发现（例如共用参数存在意图专属分布）写进汇报，继续工作。
