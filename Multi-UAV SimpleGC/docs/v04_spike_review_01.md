## 2. 17 个运行的原始时间轴诊断

### 2.1 定义与统计范围

逐机按文件接收顺序检查全部原始记录，GPI 与 SYSTEM_TIME 分流，以 `time_boot_ms` 为源时间。完整重复要求消息字典全部字段相同；外层主机接收时间不参与相等比较。时间低于该流已见高水位时优先记为回退，即便旧载荷曾经出现，也不能计作可删除的重复。异常计数指首次包之外的额外包数，例如一对相同包计 1。

`SYSTEM_TIME.time_unix_usec` 同时纳入完整内容比较，但不作为本项目单调性时钟。它的启动零值单独记录，不误判为 boot 时间回退。原始日志没有 MAVLink 帧序号、完整线缆字节和 component ID，本文的“完全重复”准确含义是**记录下来的消息字段完全相同**。

### 2.3 为什么只有 uav_01、uav_03 失效

直接原因已确定：两轮这两架飞机均出现 `8934 → 8934 ms` 的相同源时刻；旧 `ObservationStream.append` 以 `source <= previous` 判整条时间轴失效，后续 `samples` 返回空轨迹，所以地面阶段一个重复就使整场 FCU 证据不可用。

uav_02 在相应连续批次中，R1 为 `8934 → 8967 ms`，R2 为 `8834 → 8867 ms`，源时间已经前进，未触发旧检查。它也完整读取了参数，故“参数读回必然让每架飞机重复”不成立。六架次 WPNAV_* 一致；完整参数表仅有 SYSID_THISMAV、COMPASS_DEC、SIM_PLD_LON 三项随实例不同。

这能解释**为什么旧指标恰好排除这两机**，不能证明为何其底层调度恰好在同一 tick 重复。实例调度/传输批次时序是合理候选，尚无帧序号和固件内部调度证据，不能归因于奇数 sysid 或特定飞机硬件。

## 5. SIM 独立速度核对

### 5.1 实际可取得的数据与方法

逐一检查 6 份 BIN 的 FMT，只有 SIM，字段为 `TimeUS, Roll, Pitch, Yaw, Alt, Lat, Lng, Q1, Q2, Q3, Q4`，格式为 `QccCfLLffff`；没有速度字段，也没有可读取速度的 SIM2。因此，**直接真值水平速度通道在这些既有文件中不存在**。本次提供独立的 SIM 位置差分估计，标记 `sim_position_backward_difference_v1` / `auxiliary_estimate_not_FCU_gate`，没有用 GPI 或 EKF 速度补成真值。

使用源时间 \(s_i=\mathrm{TimeUS}_i/10^6\)，按 \(\hat v_E(s_i)=(E_i-E_{i-1})/(s_i-s_{i-1})\)、\(\hat v_N(s_i)=(N_i-N_{i-1})/(s_i-s_{i-1})\) 和 \(\hat v_{xy}=\sqrt{\hat v_E^2+\hat v_N^2}\) 计算，将该区间平均速度放在右端点。先按 SIM 源时间差分，再仅对时间戳作原有被动时钟映射，映射到相同 10 Hz 指标网格；不对主机接收时间差分，不平滑，不跨无效位置或超过 0.15 s 的缺口。源时间不递增时整个 SIM 速度序列失效。

独立性范围是位置与速度数值来自 BIN SIM，不来自 FCU 估计；两通道仍共享事件窗口、被动时钟映射和指标函数，并不是两套完全独立的时间基准或判定算法。

## 7. v3 观测处理建议（仅方案，未实施）

### 7.1 完整重复处理

建议 v3 在原始采集之后、观测解码与时钟拟合之前，设显式预处理阶段。原始记录保持追加且不可改写；按运行、连接会话、sysid、component ID、消息类型建立源流身份。采集记录增加 MAVLink 帧序号和解码器版本供诊断，但不能把帧序号相同单独当成可删除证据。

默认只接受与当前源时间高水位相同、完整解码载荷相同的重复，首次保留；同源时间不同内容、落后高水位的旧包回放、真正回退或无法解释的重启继续使相关时钟 epoch 失效。对未来确认的飞控重启，只能依据独立会话/重启证据切出新 epoch，并重新证明各 epoch 的时间映射，不能见到回退就自动恢复。相等性、可忽略字段清单和浮点比较均需规范化；首版不使用近似容差掩盖细微冲突。

审计输出至少含原始行号、首包行号、源/接收时间、分类、处理动作、窗口内外分布、每流计数及删除后残余异常。去重不能跨越 invalid barrier，也不能用于生成看似连续的速度或停靠证据。

### 7.2 时间单调性是否只查观测窗口

**不建议把全局检查直接改成“只检查窗口内”。建议保留全生命周期审计，再把任务指标资格与明确窗口分层。** 起飞前的时钟重置也可能破坏观察阶段使用的模型；先裁数据再检查会隐藏这些问题。

建议拆成两层：

1. 全局时间与源身份层：对完整源流审计，构造可证明的时钟 epoch，确定每个任务窗口属于哪个 epoch；所有异常均留存。遇到窗口外冲突/回退，默认该 epoch 不合格，除非另有明确、版本化且可验证的隔离依据。
2. 指标窗口层：覆盖只使用正式 service window；到达与停靠使用自己的物理窗口，并包含声明的左右插值支持区间、到达搜索范围与判停持续时间所需样本。窗口外纯重复按统一规则去重；不让无关地面重复无条件抹掉整个有效飞行。窗口边缘缺证据或跨 epoch 时保持 UNKNOWN。

本次修复本身已经说明：先区分完全重复与真实时间错误，即可恢复两轮证据，**无需同时放宽单调性检查范围**。建议 v3 第一版先采用显式去重 + 全流严格检查，再单独验证窗口资格分层；避免一次更改两个语义而难以归因。飞行安全间距窗口应保留整个飞行范围，不能缩短成 observe。

### 7.3 版本化与兼容策略

建议在未来 v3 结果清单中明确保存以下独立字段；这些名称是拟议版本，不是本轮已实现的生产字段：

| 字段 | 拟议首版值 / 用途 |
| --- | --- |
| `observation_processing_version` | `v3_observation_v1`，与 TaskSpec 版本分开 |
| `duplicate_policy_version` | `exact_duplicate_drop_v1`，复用前须固定比较协议与源身份 |
| `timeline_policy_version` | `full_stream_strict_v1`；若引入 epoch + 窗口资格，另发新版本 |
| `window_policy_version` | 声明各指标实际窗口及边界支持区间 |
| `clock_model_version` | 显式固定训练/验证拆分与去重发生顺序 |
| `metric_version` / `quality_policy_sha256` | 指标与门禁绑定，不由最新软件隐式替换 |
| `source_sha256` / `analysis_source_sha256` | 原始数据及分析代码哈希 |

v1/v2 继续走原处理器和原默认策略，既有 bound analysis / 数据集不重写。v3 显式选择新处理器；重分析写新目录，并在清单中绑定上述版本，不把 v2 旧 UNKNOWN 就地更新为通过。新增 TX 审计建议记录请求类型、sysid/component、缺项索引、主机发送前后时间、成功/异常以及请求关联 ID，以便今后真正对齐请求与响应。

实现前后的验收应分别覆盖：窗口内/外完全重复、同时间内容冲突、延迟旧包、真回退、接收逆序、重启 epoch、跨流身份、窗口边缘插值依赖、SIM 缺测、去重导致时钟训练拆分变化，以及 v1/v2 固定样本输出不变。这一节只有方案，本轮没有添加 v3 生产分支。
