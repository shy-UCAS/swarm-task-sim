## 1. 目标与范围

采用一个总控制器调度、按 family 静态分片、片内串行、片间并行、结束后统一导出的方案。第一阶段交付两路并行，设计支持四路；是否启用四路由后续负载与质量验证决定。

不引入消息队列、数据库、动态扩缩容、多机调度或自动故障修复。保留已有分析、导出和描述模块，避免借并行开发修改算法阈值、物理参数或既有判定。

现有 v0.5 批量循环不能直接启动多个副本：[run_v05_batch.py](../scripts/run_v05_batch.py) 第 37 行起使用固定输出位置，控制流程还假设单个 `active_attempt`。新增并行入口，不修改旧批量脚本的行为。

## 2. 分片与执行结构

先一次性生成、校验并冻结完整任务清单，然后按 family 分成 K 片。

- 同一 family 下的两种意图及其变体全部进入同一片。
- 保留原任务编号、场景、种子、family ID、profile 和输入哈希。
- 不在每片重新生成场景，不把各片的任务编号重新从零开始。
- 分片分配在准备阶段写入计划，此后恢复沿用该分配。
- 总控制器最多为每片启动一个执行进程。执行进程完成一个任务、写出结果后退出；分片中的下一个任务由总控制器继续派发。

```text
总控制器
├─ 分片 0：任务 A → 任务 D → …  独立目录、台账、端口
├─ 分片 1：任务 B → 任务 E → …  独立目录、台账、端口
└─ 所有任务结束 → 合并记录 → 统一导出、审计、描述、加载检查
```

场景与任务种子的生成依据见 [generation_v2.py](../swarm_sim/generation_v2.py) 第 40、44 行起；生成包的完整性检查见 [generation.py](../swarm_sim/generation.py) 第 210 行起。应复用完整包校验与任务 ID 选择，不能随意剪裁受哈希绑定的 JSON。

## 3. 目录、端口与写入责任

每个新批次使用全新的输出目录，禁止放入冻结归档或覆盖已有批次。

```text
parallel_batch/
├─ plan.json                 # 冻结任务分配、输入哈希、端口配置
├─ control.json              # 全局预算、完成顺序、停止状态
├─ controller.log
├─ shards/
│  ├─ shard_00/
│  │  ├─ ledger.json         # 分片台账
│  │  └─ attempts/
│  │     └─ <attempt_id>/
│  │        ├─ run/          # 本次 SITL、日志、参数、轨迹
│  │        ├─ analysis/     # 正式版本分析
│  │        └─ result.json   # 完成结果及证据引用
│  └─ shard_01/…
├─ dataset/
└─ language/
```

写入责任：

1. 总控制器独占写入全局状态和各分片台账；分片台账是任务与尝试记录，全局状态引用记录并维护全局顺序和停止状态。
2. 执行进程只写自己的 attempt 目录，不与其他进程共同修改台账。
3. 同一批次只允许一个总控制器，以操作系统文件锁阻止重复启动。
4. 结果写入临时文件后原子替换；控制器验证证据后才登记完成。跨文件中断通过结果证据和幂等登记恢复，不假设多个 JSON 能同时原子提交。

建议每片分配 100 个端口：

| 分片 | 基础端口 | 分配范围 |
|---|---:|---|
| 0 | 19100 | 19100–19199 |
| 1 | 19200 | 19200–19299 |
| 2 | 19300 | 19300–19399 |
| 3 | 19400 | 19400–19499 |

底层按基础端口加无人机序号乘 10 分配，每机使用独立工作目录及参数文件，见 [processes.py](../swarm_sim/processes.py) 第 28–62 行。准备阶段检查端口范围、无人机数量、范围之间的重叠和已有占用。

端口探测不是永久占用，探测之后仍可能有外部进程抢占；实际启动失败必须如实记录。不同运行使用相同局部实例编号是否还触发固件内部共享资源，需要后续有限仿真验证，不能仅凭静态分析宣称完全隔离。

正常清理仅针对本次启动的进程句柄，不按进程名批量结束 SITL，避免误杀其他分片。现有清理实现见 [processes.py](../swarm_sim/processes.py) 第 78–89 行。

## 4. 全局停止与预算

滚动规则由总控制器统一执行，不允许每片独立计算一套“最近 20 次”。

| 情况 | 拟采用的处理 |
|---|---|
| 已确认的真值间距、机载参数、起飞前参数或固件、受保护文件违规 | 触发全局停止，停止派发新任务 |
| 单次质量不合格 | 保留运行，计入异常窗口 |
| 任务失败、标签不一致 | 保留运行，计入异常窗口 |
| 同次运行出现多项异常 | 只计一次异常运行 |
| 时序进度差、过点速度等执行指标 | 记录，不单独停止 |
| 最近最多 20 次完成运行中异常达到 5 次 | 触发全局停止 |
| 基础设施故障、磁盘不足、结果完整性无法确认 | 单独报告原因，不伪装成任务语义失败 |

“无法核实”不等于“确认违规”。不能直接将底层 r1.2b 分析返回的全部 `hard_failures` 用作立即停止列表：当前有效口径还包含控制器中的二次判定。实现时应保留 [run_v05_batch.py](../scripts/run_v05_batch.py) 第 175 行起 `assess_artifacts` 中确认违规与未知状态的区分，并以测试固定该行为。本文不授权新增或放宽门禁。

并行下的拟定顺序：

- 按总控制器验证并登记结果的顺序，生成持久化完成序号并计算滚动窗口。
- 不用 UTC 时间排序，避免主机时钟或历史日志时间异常影响窗口。
- 导出使用原始任务顺序，与滚动窗口的完成顺序分开。
- 触发停止后保持停止状态，不因后续收尾运行的结果使窗口变化而自动解除。
- 停止派发新任务；已经在飞的任务完成降落、清理和证据保存。
- 报告区分触发停止的运行与停止后收尾完成的运行。

因此，K 路并行触发停止时，最多还有 K−1 个其他任务正在执行。这是并行设计相对串行的明确行为变化，实施时需要写入对应运行规则。

尝试预算在全局统一管理。先登记 attempt 并占用预算，再启动执行进程；不能让各片分别获得一份完整预算。磁盘检查也按全批次剩余任务、在途任务及统一导出空间计算，不能把同一份空闲空间重复分配给每片。

不同生产阶段的滚动窗口保持独立，不将验证阶段或上一阶段的记录混入新阶段。

## 5. 中断与恢复

| 已有状态 | 恢复动作 |
|---|---|
| 结果及分析完整、证据哈希通过，但控制器尚未登记 | 幂等补登记一次，不重飞 |
| 执行进程仍在运行 | 不重复启动该任务 |
| 只有部分证据，无法确认完成状态 | 标记待处理并停止恢复，不自动重飞 |

第一版不自动重试、不自动修复、不自动清理遗留进程，也不自动返还已占用尝试预算。

现有任务执行器有中断任务再次执行的恢复路径，见 [run_mission_list.py](../scripts/run_mission_list.py) 第 181 行起。新控制器不能未经核对直接调用其 `resume`；恢复必须先判断证据与进程状态，避免将“状态缺失”解释为“从未起飞”。

控制器启动、结果接收与恢复都应校验任务归属、正式分析选择及证据哈希。执行进程的退出码不能单独代表全局门禁结论，任务语义失败与基础设施故障必须根据结构化结果区分。

## 6. 统一分析与收尾

正式分析复用已有 progress v2、巡逻验证 v2、统一语义 v3 对应链路，不因并行新增算法版本。分析写入新目录并明确绑定来源，不覆盖原分析。

合并前检查：

- 任务集合没有遗漏、重复或混入其他批次。
- 每个任务绑定明确的原始运行和正式分析目录。
- 场景、配置、质量策略、分析版本与证据哈希一致。
- 所有执行进程完成收尾，不能把部分完成的批次标记为全部完成。

数据导出按原始任务清单顺序进行；导出 API 保留输入顺序，见 [dataset.py](../swarm_sim/dataset.py) 第 20、47 行起。family 划分沿用相同 family ID 和 split salt，见该文件第 15 行起。

质量不合格运行继续保留在台账和证据中；全量导出保留质量标记，算法取数按现有资格规则排除，不通过删掉失败记录提高质量合格率。

描述在统一导出之后生成。当前描述选择依赖数据集清单哈希，见 [language_v0.py](../swarm_sim/language_v0.py) 第 103 行起；不能各片独立生成描述后直接拼接。

完整收尾顺序：合并核对 → 导出 → 审计 → 描述生成及一致性检查 → 加载检查 → 汇总报告。报告继续单列巡逻阶段时序进度差的中位数、最大值与超限比例，作为诊断，不新增门禁。

确定性目标是任务输入、种子、family 和划分规则不因执行顺序改变，不承诺串行与并行轨迹逐字节相同。主机调度、接收时延、运行 ID 和来源路径会影响运行结果或清单字节内容。

## 8. 离线测试与实施顺序

### 8.1 必须覆盖的离线测试

1. K 为 1、2、4 时，任务集合完全一致、无遗漏或重复，family 不拆散，场景和种子不变。
2. 各片端口范围、参数文件、临时文件和输出目录互不覆盖；拒绝覆盖已有批次或写入冻结归档。
3. 使用假执行进程制造乱序完成，验证并发下预算正确、台账不丢记录、完成序号可重放。
4. 异常来自不同分片时，第 5 次异常仍触发全局停止；同次多项异常只计一次；窗口只取最近最多 20 次。
5. 单次质量不合格及无法核实不误触发立即停止；已确认的间距或其他关键违规会触发。
6. 停止后不派发新任务，已启动任务可以收尾，停止状态不自动解除。
7. 在登记、执行、结果落盘和控制器登记阶段模拟中断，恢复不重复执行或重复计数。
8. 一个分片清理进程时不影响另一个分片。
9. 导出顺序、分析绑定和 family 划分正确；描述基于统一数据集生成。
10. 原有相关离线回归通过，历史证据与判定保持不变。

## 9. 有限仿真验证建议

首轮建议选择 4 个 family、8 个任务，覆盖两种意图、不同机数及适当的返航设置；分别串行和两路执行，共 16 次新运行。所有证据另存，不能重写 v0.5 原运行。

比较总耗时、合格 episode/小时、CPU/内存、采样间隔及各类时钟不可用原因。小样本用于发现并行问题，不能据此宣称质量失败率已经得到充分验证。

两路通过后才考虑四路。不得因并行出现时钟问题而自动放宽质量阈值，也不因 CPU 尚有空闲就直接提升路数。实际任务选择、运行预算与开始时间另行授权；本文不启动这些验证。

## 10. 负载与耗时预期

本机核对结果：AMD Ryzen 9 9950X3D，16 个物理核、32 个线程，内存约 64 GiB。未取得可靠的历史单次运行 CPU 占用记录，因此路数建议不是基于已测 CPU 利用率推算。

从两路开始的原因：CPU 总量之外，接收线程与采样线程的调度时延也会影响时钟模型。现有证据间隔超过 2 秒、速率范围和接收残差等判定不能因并行而放宽，见 [truth.py](../swarm_sim/truth.py) 第 26 行起。

v0.5 的 260 次试生产及批量运行日志中，有效的单次总耗时样本为 259/260，平均约 256 秒；B038 外层 UTC 时间记录不一致，未纳入该耗时均值。排除只作用于耗时统计，不修改运行原判。此均值不含全批次统一收尾或人工暂停，也不能视为 v0.6 新 profile 的保证。

按规模估算，正文公式为 \(T \approx R \times 256 / (3600 \times K \times \eta) + T_{\text{收尾}}\)。其中 \(R\) 是运行数，\(K\) 是并行路数，\(\eta\) 是实测并行效率，\(T\) 单位为小时。

以 1,000 次运行、复杂度接近 v0.5 为例：

| 配置 | 估算，不含统一收尾 |
|---|---|
| 串行 | 约 71 小时 |
| 两路，理想效率 100% | 约 35.6 小时 |
| 两路，假设效率 80%–90% | 约 39.5–44.4 小时 |

80%–90% 只是用于估算的假设，后续必须由验证结果替换。v0.6 规模尚未确定，因此不据此承诺总交付时间。
