# v0.3 实现、仿真能力与验证报告

本轮在 `Multi-UAV SimpleGC` 实现 TaskSpec v2 的共享矩形区域观察任务。保留原有 v1 三类几何任务、执行场景 schema 1、ArduCopter SITL、MAVLink 通信和数值质量策略。源码版本为 0.3.0；基线提交为 `0ea70a2ae08cf76d2b34322fa47e466659a20bdf`。原始 `SimpleGC` 未修改。

交付验证结果：140 项自动化测试通过；100 个逻辑场景生成与绑定复核通过；正式最小矩阵包含 4 次完整飞行和 1 次预期受控失败；另选定的 10 个试生产场景全部完成并通过默认数据资格。严格合格样本为 0，原因是本轮时钟质量均未达到 strict；具体分母、实跑与重分析区别见第 5 节。

这是集中式任务分解与独立飞控执行的数据闭环。它能检验指定理想观察模型下的任务结果；不等同于真实侦察效果、分布式协商或物理锁步仿真。

## 1. 实现内容与调用链

规划阶段按照每架机在同一阶段可能独立推进的情况检查整段路径，不只检查两个同步端点。所需名义净距为 \(d_{\min}+2m\)，其中 \(m\) 为跟踪裕量。等待填充保留在每机目标中，明确标成 `idle_padding`，不提供观察服务。

## 2. 成功、失败与未知如何判定

观察区离散成公共网格，覆盖率为 \(C=|\bigcup_i G_i|/|G_R|\)。集合来自有效观察阶段的实际轨迹及理想水平圆盘，重复覆盖只计算一次。进入、返回、调度等待和 idle 不算观察服务，超出声明高度容差的轨迹也不提供覆盖。

SIM 与 FCU 分别计算覆盖和返回。真值侧结果作为 `mission_success`，观测侧为 `mission_success_observation`，并记录 `semantic_consistency`。已知失败优先于其他未知子条件；没有已知失败时，缺失关键证据保留 `null`，完整证据未达标为 `false`。已有有效覆盖足够时，覆盖子条件可为 `true`，数据完整性仍另外决定样本资格。任务完成事件本身不能替代位置证据。

返回验证使用本机生成点及声明高度/到达容差，确认有效驻留。源时钟可用时，驻留和航时以源时间衡量；输出明确记录末端采样容差，不宣称连续时间的严格证明。

`run` 进程执行完成、任务语义成功和数据集合格是三个不同结论。默认合格样本必须通过原有观测、真值、时钟、执行和间距保护，并同时满足双通道任务成功、判断一致及生命周期硬约束。

数值策略 `quality_policies/default_v022.json` 未放宽：时钟残差 strict 为 20 ms、acceptable 为 50 ms；默认集合接受二者，严格集合仅接受 strict。它们是被动映射的诊断残差，不是绝对同步精度。

生命周期世界范围规则为：水平边界和高度上界贯穿解锁至落地；巡航高度下界只作用于 `airborne_ready` 至 `landing_started`。起降过渡阶段不适用巡航高度下界。所有机对间距检查包括尚未起飞或已落地的邻机。速度、爬升和加速度只报告执行后代理值，当前不作为经标定的物理约束证明。

## 3. 执行衔接修复与保留的失败

首次 v2 实跑 `runs/recon_shared_demo_3uav_20260930T150647Z_dbbe253b` 在第一阶段后失败：LOITER 下默认低油门使飞机下降，uav_02 无法达到 1 m 驻留确认，原始消息记录了触地。该目录与失败分析完整保留。

修复后，v2 在起飞保持与航点上传时使用 BRAKE，等待下一阶段时保持 AUTO 航点控制，几何驻留通过后才进入下一阶段。旧 v1 的执行方式保持兼容。没有降低到达、覆盖、间距或质量门槛。模式选择依据与 [ArduPilot BRAKE 说明](https://ardupilot.org/copter/docs/brake-mode.html) 中不接受驾驶杆输入的行为一致。

首次修复后真实闭环为 `runs/recon_shared_demo_3uav_20260930T151518Z_739c4d31`：双通道覆盖 1620/1620 网格，任务与返航成功；默认合格、严格不合格。当时开发版本导出到 `datasets/v03_first_closure_20260930`，成功加载得到 \(1189\times3\times6\) 观测和对应掩码，体检无问题。该历史导出使用旧语义规则，最终加载器不直接接收它；需要新建当前规则的分析和导出才能用于当前实验。

该开发过程样本有助于追踪修复，但正式验证和试生产结果单独列于下文。第一次成功仅证明该配置的闭环，不证明任意布局或长期稳定性。

正式矩阵的第二次三机和两机运行还发现了末端证据截断：原始遥测存在，但语义分析仅收到截止于最后一个输出网格的轨迹，丢失了插值到事件结束时刻所需的后一个支撑点。旧分析因此输出 FCU 返回未知，并正确排除样本。

修复仅让 v2 语义验证保留末端额外支撑点，再按原事件窗口裁剪；观测 CSV 的时间网格、任务阈值和质量门槛保持不变。无效点、缺口和时钟范围仍不能被外推或跨越。规则版本更新为 `shared_coverage_v2`，旧分析保留，新分析另存；报告区别实际飞行与后续离线重分析。

版本复核还发现过 manifest 已升级、标签来源仍使用旧常量的不一致。最终将版本常量集中维护，并在数据边界增加跨文件一致性检查。开发期导出保留用于追踪，正式导出由统一版本的分析重新生成；没有手工修改任何成功标签或飞行原始数据。

## 4. 证据、协议与兼容性

新分析除原有 CSV、task/labels/quality 外，增加 `mission.json`、`shared_scene.json`、`allocation.json`、`semantic_plan.json`、`semantic_validation.json`、`phase_windows.json`、`execution_constraints.json` 和 `lifecycle_clock_models.json`，均由 manifest 哈希覆盖。

使用到的原始遥测、事件、场景、元数据、选定 BIN 和存在时的三份生成来源文件均进入来源哈希。选定 BIN 因 SIM 时间戳异常而无法提供真值时，该失败 BIN 仍记录来源哈希。多个 BIN 导致无法选定时不会声称已使用它们。重新分析前还核对两个场景来源一致，不静默接受矛盾输入。

语义协议包括 `task_kind`、ontology、label schema、semantic validation、eligibility 和 `execution_constraints_version`；最终 v2 语义规则为 `shared_coverage_v2`，生命周期规则为 `execution_limits_v2`。版本常量由协议模块统一提供；导出、读取和恢复还核对质量文件、语义报告、约束报告、标签来源与行为规则的版本一致性，不能只凭文件哈希通过。不同语义协议或数值策略不混合导出。历史 v0.2.x 清单按明确旧协议识别，不自动改成新任务标签。

生成器的 family 对应同源基础实例；变体及后续尝试继承 family，run/attempt 分别使用独立身份。恢复核对冻结的输入、代码、固件、参数、策略及选定分析的全部证据；成功目录存在而证据损坏时拒绝跳过。代码改变后必须使用新的执行目录。

加载器返回标准 Python 嵌套列表，无新增 NumPy 依赖。缺失观测填零并令 mask 为 false。标签、任务、真值、参考航点、family 和上下文都不进入六个观测特征。

## 5. 验证方法与实测结果

验证使用项目 `llm` 环境、本机随工程提供的 ArduCopter、速度倍数 1。未安装依赖，未关闭飞控检查。基线和环境详情见 [基线核对](v03_baseline_check.md)。

证据分为四类：单元/回归测试；手工构造、预期可计算的语义轨迹；日志离线分析；本轮真正启动的 SITL。本轮没有把之前版本的历史实跑算作新运行；本轮飞行之后的重分析单独标明，不重复计算飞行次数。

## 6. 当前能力边界与后续顺序

当前支持 1～6 架同构飞机、一个轴对齐矩形、固定观察高度、一个 reconnaissance/area_coverage 任务和两个条带方向，最多 100 个执行阶段。非空禁区、不支持的模型和超出预算的输入明确拒绝。

固定 profile 和 seed 保证任务生成与编译的确定性；不保证独立 SITL 的主机调度、被动时钟拟合或每个遥测采样逐点复现。实际新运行验证覆盖 2/3/6 机；1 机分区有逻辑测试，4/5 机没有本轮单独实跑证据。

理想圆盘覆盖不含遮挡、相机视场姿态、探测概率、传感器噪声或未知身份目标。多个 SITL 没有统一碰撞物理；阶段屏障是集中式调度，没有在线避碰、通信网络模型和分布式协商。规则生成的任务标签也不保证单凭轨迹就能识别高级意图。

后续建议依次推进：

1. **先标定执行约束。** 对爬升、速度和加速度代理值与飞控设置建立对应关系，再决定哪些成为硬门槛。当前实测爬升代理约 2.27 m/s，超过名义 2 m/s，因此不能宣称已验证所有平台动力学限制。
2. **减少阶段屏障开销。** 在保留独立服务窗口与来源证据的前提下，探索每机完整 AUTO 路线和任务事件标记，比较等待时间及重复性。
3. **增加有区分度的第二类任务与对照。** 先设计反捷径场景、跨布局/速度/机数的 family 分割，再评估任务或意图识别。不要从单类成功率推导分类能力。
4. **按需求升级观察与地图。** 传感器模型、非矩形区域、禁区和障碍规划应各自定义新协议并配套独立验证；不在当前模型上仅增加字段。
5. **扩大数据前先看试生产。** 根据失败、未知、时钟等级、模板集中度和拆分分布决定下一批规模。保留失败和变体关系，避免只收集通过样本。

本轮未自动提交或推送。原始证据目录体积会随真实运行增加；正式实验应保存这些证据及其清单，而不能只保留最终成功标签。
