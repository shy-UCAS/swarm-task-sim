# v0.5 起始朝向问题复盘与修补方案

**文档日期**：2026-10-02  
**状态**：待决策  
**背景**：v05b 和 v05c 连续验证失败后的技术审查

---

## 1. 当前纠结的问题

### 1.1 问题表象

在 v0.5 双意图数据集的实施过程中，遇到两次连续的验证失败：

**v05b 失败**（验证预算 1/8）：
- 原因：`SIM_PLD_YAW` 参数差异（预期 273.4°，实际 181.6°）
- 根因：起始航向随机 → 参数值不可预测 → 参数门禁失败

**v05c 失败**（验证预算 2/8）：
- 修改：固定所有飞机起始航向为 0°（`heading_policy="fixed_zero"`）
- 结果：参数门禁通过，但出现新问题：
  - **AV-4 失败**：approach 阶段时序超限（D=5.907s > τ=4.022s）
  - **AV-1 失败**：27 个中间航点中 9 个证据未知
  - **AV-2 失败**：uav_01 停靠 5 次，超过限值 4 次
  - **AV-8 失败**：uav_03 圈数为 null（证据不足）

### 1.2 问题本质

我们在围绕**起始朝向**这个变量进行反复调整：

```
随机朝向 → 参数不可预测 → 固定朝向 → 几何约束超限 → 需要再调整？
```

已消耗验证预算 **2/8**，但核心问题仍未解决。

---

## 2. 对这个问题的态度：过度设计

### 2.1 起始朝向的真实重要性

**对飞行轨迹的实际影响**：
- ArduCopter 起飞后会自动转向第一个航点
- 起始朝向只影响**最开始 2-3 秒的转向动作**
- 进入巡航后，轨迹完全由航点序列决定，与初始朝向无关

**对意图识别的实际影响**：
- **几乎为 0**
- 模型识别的是"区域内往复扫描 vs 边界循环巡逻"的宏观模式
- 不会依赖"起飞时朝哪个方向"这种瞬时特征

**对参数 `SIM_PLD_YAW` 的影响**：
- 这个参数只是"降落伞朝向"
- 对飞行性能、轨迹形态、任务成功率**没有实质影响**
- 是一个纯粹的"记录性参数"，不是"控制性参数"

### 2.2 系统设计放大了这个问题

**问题不在朝向本身，而在于系统架构**：

1. **参数验证过于严格**
   - 要求所有参数（包括 `SIM_PLD_YAW` 这种无关参数）完全一致
   - 没有区分"控制性参数"和"记录性参数"
   - 没有区分"固定参数"和"场景派生参数"

2. **场景布局设计有缺陷**
   - `random_spawn_v2` 的分层区域策略（N × unit）+ line 编队
   - 某些（编队方向，进场侧）组合天然导致距离差大
   - 原本依赖"随机朝向碰巧化解"这种不确定性

3. **修复策略治标不治本**
   - v05b → v05c：固定朝向只是"绕过参数验证"
   - 但没有解决"场景布局不合理"的根本问题
   - 反而暴露了几何约束问题

### 2.3 时间成本与收益不成正比

**已投入**：
- v05b 设计、实现、DR、验证失败 → 约 2 周
- v05c 修改、DR、验证失败 → 约 1 周
- 当前复盘与方案讨论 → 约 2 天

**总计**：约 3.5 周，消耗验证预算 2/8

**实际收益**：
- 对最终数据集的意图识别能力**几乎没有提升**
- 对 benchmark 可信度**没有本质改善**
- 只是在"满足一个过严的形式化验证规则"

**机会成本**：
- 本应用于实现第二种执行策略、捷径探针、分布外测试等**真正影响 benchmark 质量**的工作

## 3. 判断：不应继续在此问题上投入

### 3.1 核心观点

> **起始朝向不是 benchmark 设计的关键变量，不应让它成为阻塞整个项目的瓶颈。**

**理由**：

1. **对意图识别的贡献极小**
   - 意图的本质区别在于"区域覆盖 vs 边界巡逻"的语义差异
   - 不在于"起飞时朝向 0° 还是 45°"

2. **当前困境是架构债务**
   - 参数验证系统设计于 v0.3 单一意图阶段
   - 未考虑"参数可能依赖场景随机性"的情况
   - 升级验证系统的成本远大于"固定朝向"，但我们不应为了迁就旧设计而扭曲新设计

3. **修订版 r1 的定位**
   - 文档开头明确说明：这是"**最小双意图数据集**，用于让算法链路跑起来"
   - "**不能用来报告意图识别准确率**"
   - 既然是"最小数据集"，就应该**快速迭代、尽早交付**，而不是追求每个细节完美

4. **真正影响 benchmark 质量的工作还没做**
   - 每种意图只有一种执行策略（留出策略测试未做）
   - 没有捷径探针（无法验证模型是否学到语义）
   - 没有分布外测试划分（无法评估泛化能力）
   - 这些才是 v0.6 及以后应该重点投入的方向

## 4. 修补方案：务实的最小改动

### 4.1 指导原则

- **时间优先**：1 周内完成修补，恢复验证流程
- **风险最小**：不推倒 v05c 的已有工作
- **文档诚实**：在数据契约中如实标注已知限制

### 4.2 推荐方案：分阶段 τ + 场景筛选

#### 第 1 步：放宽 approach 阶段的时序容差（2 小时）

**理由**：
- approach：从起点到入口，距离差由场景几何决定，**规划器无法优化**
- patrol：沿同一环线飞行，间距是规划器精心设计的，**应该严格控制**
- 分阶段设置体现了"不同阶段约束来源不同"

**修改**：
```python
# swarm_sim/mission_v3.py 或相关位置
def get_timing_tolerance(phase_type, phase_duration, config):
    min_s = config.get("min_s", 3.0)
    fraction = config.get("fraction_of_phase", 0.2)
    
    # 分阶段上限
    if phase_type == "approach":
        max_s = config.get("approach_max_s", 7.0)  # approach 放宽到 7s
    else:
        max_s = config.get("max_s", 5.0)  # 其他阶段保持 5s
    
    return max(min_s, min(fraction * phase_duration, max_s))
```

#### 第 2 步：验证场景选择时增加预筛选（4 小时）

**实现**：在选择 VP1-VP6 的场景时，优先选择 approach 距离差较小的场景

```python
# 新建脚本：scripts/select_balanced_validation_scenes.py
def select_validation_scenes(dr_result, num_required=6):
    """从 DR 结果中选择 approach 几何平衡的场景"""
    candidates = []
    
    for base_idx, base_record in enumerate(dr_result["accepted_bases"]):
        # 计算该场景下 patrol 任务的 approach 距离
        patrol_record = base_record["missions"]["patrol"]
        approach_plan = patrol_record["plan"]["approach"]
        sampled = base_record["sampled"]
        
        distances = []
        for i, vehicle in enumerate(sampled["spatial_slots"]):
            start = (vehicle["east_m"], vehicle["north_m"])
            target = approach_plan["routes"][i][0]  # 第一个航点（入环点）
            dist = math.dist(start, (target["east_m"], target["north_m"]))
            distances.append(dist)
        
        distance_range = max(distances) - min(distances)
        
        # 记录距离差
        candidates.append({
            "base_index": base_idx,
            "distance_range": distance_range,
            "max_distance": max(distances),
            "min_distance": min(distances),
            "vehicle_count": sampled["vehicle_count"],
            "entry_side": sampled["entry_side"]
        })
    
    # 按距离差排序
    candidates.sort(key=lambda x: x["distance_range"])
    
    # 选择前 num_required 个，确保覆盖不同 N 和进场侧
    selected = select_stratified(candidates, num_required, 
                                  strata=["vehicle_count", "entry_side"])
    
    return selected
```

### 4.3 备选方案：如果第 4 步仍失败

**放宽验证门禁**（务实妥协）：

```markdown
### 验证运行容错规则（修订）

原规则：任一验收项不通过即停止

新规则：
- 6 个 VP 中至少 **4 个完全通过** AV-1 到 AV-8
- 剩余 2 个允许以下"软失败"：
  - AV-1 或 AV-8 为 null（证据不足，但不是硬性错误）
  - AV-4 的 D 超限但 < τ + 2s（轻微超限）
- 以下仍为"硬失败"，立即停止：
  - AV-3（双通道不一致）
  - AV-5/6/7（硬性错误）
  - 真值最小机间距 < 5m
```

**理由**：
- null 不等于"确实失败"，只是当前分析能力的边界
- 轻微超限（<2s）在工程上可接受，不影响数据集整体质量
- 硬性错误（间距违规、参数错误）仍然零容忍

## 5. 长期建议：v0.6 的架构改进

### 5.1 参数验证系统重构

**目标**：区分"固定参数"和"场景派生参数"

```python
class ParameterValidator:
    FIXED_PARAMS = {
        "WPNAV_SPEED": 300.0,  # 控制性参数，必须固定
        "LAND_SPEED": 50.0,
        # ...
    }
    
    DERIVED_PARAMS = {
        "SIM_PLD_YAW": lambda scene: scene.vehicles[0].heading_deg + 0,
        # 可以是函数，给定场景计算期望值
    }
    
    IGNORED_PARAMS = {
        "SIM_TERRAIN_MODEL",  # 记录性参数，不影响飞行
        # ...
    }
    
    def verify(self, scene, actual_params):
        for name, actual in actual_params.items():
            if name in self.FIXED_PARAMS:
                expected = self.FIXED_PARAMS[name]
                if actual != expected:
                    raise ParameterMismatch(name, expected, actual)
            
            elif name in self.DERIVED_PARAMS:
                predictor = self.DERIVED_PARAMS[name]
                expected = predictor(scene)
                if abs(actual - expected) > tolerance:
                    raise ParameterMismatch(name, expected, actual)
            
            elif name in self.IGNORED_PARAMS:
                # 只记录，不验证
                log.info(f"{name} = {actual} (ignored)")
```

### 5.2 场景采样器升级

**目标**：采用扇形分布或其他几何平衡的布局

```python
# random_spawn_v3: 扇形分布
def sample_random_spawn_v3_scene(...):
    # 飞机在进场侧呈弧形排列，都面向入口
    # 每架飞机到各自分配目标的距离基本相等
    # approach 阶段距离差 < 5m → 时间差 < 2s
    ...
```

**预期收益**：
- 恢复朝向的自然多样性（可以随机，也可以固定）
- approach 几何约束自然满足 τ=5s
- 无需分阶段设置容差

## 7. 总结

### 核心观点

> **起始朝向是一个被过度设计放大的问题。它对意图识别的实际贡献极小，不应成为阻塞项目的瓶颈。**

### 行动建议

1. **短期（v0.5）**：务实修补，快速交付，诚实标注限制
2. **长期（v0.6）**：架构重构，系统性解决参数验证和场景布局问题
3. **投入重心**：转向真正影响 benchmark 质量的工作（多策略、探针、分布外测试）

### 教训

- 不要让形式化验证规则绑架设计决策
- 区分"关键路径"和"边缘问题"
- "最小数据集"阶段应该快速迭代，而非追求完美
- 技术债务应该在合适的时机偿还，而非在紧急交付阶段
