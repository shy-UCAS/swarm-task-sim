## 2. 根因（一轮影响定位）

### 2.1 直接错误

两次运行的 `metadata.error` 与 `runner_error` 完全相同：

```text
ValueError: invalid parameter index/name/value in readback
```

该字符串在仓库中唯一出现在 [run_provenance.py:257-258](../swarm_sim/run_provenance.py#L257-L258)：

```python
                if not 0 <= index < count or not name or not math.isfinite(message.param_value):
                    raise ValueError("invalid parameter index/name/value in readback")
```

### 2.2 触发报文

两次尝试的原始 `raw/uav_0X.jsonl` 中，回读窗口内收到的 `PARAM_VALUE` 形如（原样摘录）：

```json
{"recv_monotonic_s": 5129.1251344, "sysid": 1, "message": {"mavpackettype": "PARAM_VALUE", "param_id": "GND_ABS_PRESS", "param_value": 101179.75, "param_type": 9, "param_count": 1202, "param_index": 65535}}
```

`param_count=1202` 合法，但 `param_index=65535`（MAVLink 中表示"索引不可用"）。`0 <= 65535 < 1202` 为假，于是立即抛错。结果是回读**一个值都没接受**：`parameter_count=1202`、`received_count=0`、`status=failed`、`complete=false`，参数比对里每个参数都是 `reference_value=<基线值>`、`observed_value=null`、`pass=false`。

### 2.3 为什么这次落进窗口

v0.6 计划第 2.2 节把 `AUTOPILOT_VERSION` 等待由 10 秒改为 2 秒，实现为新 TaskSpec 字段 `execution.firmware_version_timeout_s`（[mission_v3.py:135-142](../swarm_sim/mission_v3.py#L135-L142)），经 [runner_v3.py:276-278](../swarm_sim/runner_v3.py#L276-L278) 传入 `read_firmware_parameters(..., version_timeout_s=...)`；本批 TaskSpec 实测 `firmware_version_timeout_s=2`、`protocol_version=v0.6`、`final_hold_s=2`。该等待恰好位于回读之前（[run_provenance.py:222-243](../swarm_sim/run_provenance.py#L222-L243) 的顺序是：请求版本 → 等版本 → 请求参数表），因此缩短它会**一并把参数表请求提前**。

| 时间点（相对各自运行 epoch） | 旧 20 任务 pilot（10 秒等待） | 本批（2 秒等待） |
|---|---:|---:|
| 连接建立 | 1.78 s | 1.64–1.69 s |
| 版本请求发送 | 1.78 s | 1.69 s |
| **参数表请求发送** | **11.79 s** | **3.64–3.70 s** |
| 首个带索引的 `PARAM_VALUE` | 请求后 +0.018 s | 请求后 +0.094 s |
| 启动期 `param_index=65535` 最后一条 | 不在回读窗口内（回读成功） | **请求后 +0.094–0.097 s（落在窗口内）** |
| 回读结果 | `complete`，1202/1202 | `failed`，0/1202 |
| 运行失败 | — | 请求后 +0.13 s（t≈3.77 s） |

两次尝试（共 5 架次）都是：19 条 `param_index=65535` 的启动期广播，其中最后一条在参数请求之后到达；旧批次同样存在 54–64 条同类广播，但它们都不在回读窗口内（回读成功、`received_count=1202` 即为证明）。

**结论：那次 10 秒等待在旧链路里同时承担了"等参数表就绪"的作用，而不只是等 `AUTOPILOT_VERSION`。** 版本消息本身在本固件下从未到达（本批 5/5、旧批 58/58 `autopilot_version_available=false`，一直靠二进制内嵌字符串核对），所以把 10 秒缩成 2 秒在版本核对上并无损失，**代价全部落在参数表回读上**。

## 7. 建议（只提方案与理由，本轮不实施）

两个方案都需要改源码，因此**阈值与代码冻结前不实施**，等复核决定：

- **方案 A（推荐）**：把"版本等待"与"参数表就绪"解耦。不要用固定等待兼作启动就绪判据，而是在 `PARAM_REQUEST_LIST` 之前使用明确的就绪条件（例如等到 FCU 的启动期广播结束/心跳与状态稳定），或对同一次回读保留一个短的重试窗口。理由：这恢复了旧链路实际依赖的语义，且不放松任何 P0 门禁；代价是每次尝试重新增加若干秒等待，需要在"省时"与"就绪"之间显式取值。
- **方案 B**：让回读容忍 `param_index=65535`（按 `param_id` 用 `PARAM_REQUEST_READ` 兜底或忽略该报文）。理由：该值在 MAVLink 语义上是"索引不可用"，不是参数值错误。代价与风险：这属于放宽一个 **P0 起飞前门禁的输入处理**，必须单独论证"忽略它不会漏掉真实参数差异"，并补对应测试；不能顺手改。
- 无论选哪个，都需要重新 prepare 一个新批次（本批 `stopped_reason` 不可清除、`--resume` 明确拒绝，旧批次不补飞）。
