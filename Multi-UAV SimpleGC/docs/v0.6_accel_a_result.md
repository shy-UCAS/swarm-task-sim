## 2 停止根因：基础设施故障被误判为"确认违规"（P0 级分类缺陷）

`a000004` 的原始证据：

| 证据 | 值 |
|---|---|
| `metadata.status` / `error` | `failed` / **`RuntimeError: uav_03: receiver failed: SITL closed the TCP connection`** |
| `firmware_parameters.json`（3 机） | 每机 `status=failed`、`complete=False`、**`received_count=0`、`parameter_count=None`** |
| 分析层 `validation_policy.hard_checks` | `parameter_firmware=false`、`onboard_mission_parameters=false`、`truth_separation=true` |
| 结果层 `hard_failures` | **`['parameter_firmware']`** → 控制器 `_stop("confirmed violation: parameter_firmware")` |

判据代码（`swarm_sim/validation_policy.py:45-52`，逐字）：

```python
      and set(readback) == agents
      and all(row.get("complete") is True and row.get("status") == "complete"
              and type(row.get("received_count")) is int and row["received_count"] > 0
              and row["received_count"] == row.get("parameter_count")
              and row.get("missing_indices") == [] for row in readback.values()))
...
      checks = dict(parameter_firmware=parameters_ok,
```

即：**回读不完整（本次是整行为空）与"读出不一致"被压成同一个 `False`**。对照 `onboard_mission_parameters` 的实现（`swarm_sim/parallel_worker.py:99-104`）是三值逻辑——只有 `status=="mismatch"` 或 `mismatch_count>0` 才是 `False`，无法核实时为 `None`；而 `hard_failures=[key for key,value in checks.items() if value is False]`（`:134`）只把 `False` 计入，`None` 不会触发停止：

```python
    onboard_check = None
    if onboard.get("status") == "mismatch" or finite(mismatches) and mismatches > 0:
        onboard_check = False
```

**同一个崩溃在本批产生了两级后果**：`onboard_mission_parameters` 被正确记为 `None`（仅不写入数据集），`parameter_firmware` 却记为 `False`（不可逆停止整批）。

**影响（会让哪一项研究结果出错）**：它本身不产生错误数据（该运行已被判不合格、未导出），但它**错误地终止了对照测试**，使 A 组无法完成 42 个任务的配对比较——也就是说，**本次 A 的"未通过"结论中，判据 ①③ 的一部分是由这个缺陷造成的，而不是 4 路并行本身**。若同一缺陷存在于 r3 的 900 任务路径中，**任意一次 SITL 崩溃都可能不可逆地终止整批**（r2 全程 465 次尝试无此发生，属运气/概率）。

**建议修法（不改任何阈值）**：给 `parameter_firmware`（及 `frozen_firmware_and_parameters`）与 `onboard_mission_parameters` 同样的三值语义——只有在**回读完整且与冻结表/版本确实冲突**时才为 `False`；因运行本身失败（如 `received_count==0`、`status=failed`、`parameter_count` 缺失）导致无法核实时记 `None`（仅判该运行不合格），真正的确认不一致仍然立即停止。

## 6 研究影响与建议

**会让哪一项研究结果出错？** 本批没有产出错误数据（6 次尝试中 5 次不合格、1 次合格，未导出、未收尾），因此不影响任何研究结论。**真正的 P0 是停止路径的分类缺陷**：一次与参数无关的 SITL 崩溃被当作"确认违规"，能在任意时刻不可逆终止批次（本批 6.8 分钟即终止）。若不在 r3 之前修复，900 任务的正式运行会带着同一颗地雷。

**建议（按优先级）**：
1. **修 `parameter_firmware`（及 `frozen_firmware_and_parameters`）的三值语义**（P0，见 §2），使"因运行失败导致无法核实"记为 `None`（仅判不合格），"完整回读且确实冲突"才 `False`（立即停止）。加对应单元测试（空/不完整回读 → 不触发停止；完整回读+不一致 → 触发停止）。
2. **重跑 A 组，且严格满足独占机器**（测试方案 §3.1）：关闭 `sqlservr`/浏览器/`ChatGPT`/输入法云服务/播放器等，暂停杀毒对 `SwarmData` 与 SITL 目录的实时扫描，电源计划高性能。本次的残差数据说明该条件不是形式要求——它直接决定判据 ② 是否可达。
3. **在独占条件下区分"并发"与"启动抖动"**：可考虑把 4 片的启动**错峰**（测试方案已把错峰启动列入时间语义审查项），作为独立变量验证，而不是与 K 值混在一起判。
4. **给 run 块加转录**（过程缺口，P2），否则台账重试次数这类指标无法事后取证。
5. 本次数据**不得用于训练**（`purpose=pilot`、`training_data=false`）；r1、r2 未做任何操作。
