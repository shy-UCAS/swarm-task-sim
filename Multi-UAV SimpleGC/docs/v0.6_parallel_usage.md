# v0.6 分片并行入口使用说明

本轮交付范围为准备指令第 0–6 节：代码与离线测试。完成后停在“暂停 1”。下列运行命令仅供复核后使用，本轮未启动 SITL，也未执行任何试跑；试跑规模和方案等待另行确认。v0.5 入口和旧归档 `Simulation` 保持原样，本轮不迁移已有数据目录。

## 数据根目录与准备

在 `Simulation-dev/Multi-UAV SimpleGC` 中使用 PowerShell 7，先读取项目自己的 `.conda-env`。v0.6 的所有批次数据放在 `SIM_DATA_ROOT/parallel_batch/<batch-id>/`。**`SIM_DATA_ROOT` 未设置或为空时直接报错退出，没有默认目录。** 根目录必须是绝对路径，且位于所有 Git 仓库和旧归档之外；例如固态盘上的 `E:/SwarmData`，不能使用当前仓库里的 `runs/`、`verification/`，也不能指向旧 `Simulation`。未来试跑应使用固态盘；冻结后再考虑归档介质。

```powershell
$EnvName = (Get-Content .conda-env -Raw).Trim()
$env:SIM_DATA_ROOT = 'E:/SwarmData'

# 先自行选定 profile、批次 ID、总尝试预算和磁盘估算；以下占位符需要替换。
conda run -n $EnvName --no-capture-output python scripts/run_parallel_batch.py prepare `
  --profile '<已确认的 profile.json>' --batch-id '<新批次 ID>' --shards 2 `
  --max-attempts '<全批次总尝试次数>' `
  --storage-bytes-per-attempt '<每次尝试预留字节>' `
  --export-reserve-bytes '<统一导出预留字节>'
```

上述环境变量设置只影响当前 PowerShell 进程及其子进程。新终端必须重新设置。`batch-id` 以字母或数字开头，仅含字母、数字、下划线或短横线，最长 80 字符。预算和空间估算必须显式提供正整数，不继承 v0.5 的固定预算；总预算介于任务总数与其两倍之间。每次启动前登记 attempt 并消耗全局预算，起飞前重试也占用同一预算。启动前以全批次需求统一核对一次剩余空间，不能为每片重复分配同一份空闲空间。

`prepare` 一次性生成并冻结完整任务包、SHA256、全局任务编号、family 分配和端口配置。按 family 首次出现顺序轮流分配各片，同一 family 的两种意图及所有变体都进入同一片。分片不会重新生成场景或重置任务编号；种子、family 和 split 与执行顺序无关。批次目录必须全新，不能覆盖已有批次。

## 执行、查询与显式恢复

```powershell
# 以下 run 命令会启动仿真；仅在“暂停 1”复核并确认试跑后使用。
conda run -n $EnvName --no-capture-output python scripts/run_parallel_batch.py run --batch-id '<批次 ID>'
conda run -n $EnvName --no-capture-output python scripts/run_parallel_batch.py status --batch-id '<批次 ID>'

# 仅显式恢复：核查已有证据和进程，不自动重飞中断任务。
conda run -n $EnvName --no-capture-output python scripts/run_parallel_batch.py run --batch-id '<批次 ID>' --resume

# 全部任务及执行进程完成收尾后，统一合并和导出。
conda run -n $EnvName --no-capture-output python scripts/run_parallel_batch.py finalize --batch-id '<批次 ID>'
```

每片基础端口为 `19100 + 100 × shard_index`，默认两片分别使用 `19100–19199` 和 `19200–19299`。准备/启动检查占用，独立工作目录、参数和运行目录避免覆盖。批次控制器及每片写入者均有独占约束；重复启动直接拒绝。清理只针对本次持有的进程句柄。端口探测之后仍可能发生外部抢占，实际启动失败须据实记录；离线测试不代替真实 SITL 并行隔离验证。

只有可确认的起飞前故障允许重试一次。已经起飞的失败保留为数据；中断后不会因为结果缺失自动重飞，也不退还已占预算。恢复时，完整且哈希通过的结果可以幂等补登记；仍在执行的任务不重复启动，部分证据或无法确认的状态停止恢复并报告。

## 全局窗口与停止口径

总控制器验证结果并登记完成时持久化完成序号。最近最多 20 次完成运行按此序号构成窗口，不按 UTC、日志时间或任务编号排序；同次多项异常只计一次，累计 5 次异常停止新派发。不同阶段的窗口相互独立。

确认的真值最小机间距小于 5 m、机载任务参数不一致、起飞前参数或固件门禁失败、受保护源码/配置/冻结输入哈希变化触发停止。无法核实与确认违规分别记录，不把全部分析 `hard_failures` 当作立即停止条件。

基础设施故障沿用 v0.5 修正 B098 后口径：运行状态失败，但正式分析正常生成、证据完整时，保留数据并作为质量不合格计入窗口；分析报错、产物缺失或结果完整性无法确认时，停止派发并记录原因。停止状态不会因后续窗口变化而自动解除。已经在飞的任务继续降落、清理和保存证据，报告分别标记触发停止和停止后收尾的运行。

## 一次批次的目录结构

以下以 `SIM_DATA_ROOT=E:/SwarmData`、`batch-id=reviewed_batch_01` 为例；这是目录说明，未在本轮创建或运行该批次。

```text
E:/SwarmData/
└─ parallel_batch/
   └─ reviewed_batch_01/
      ├─ bundle/                      # 完整生成包，所有分片共用冻结输入
      │  ├─ mission_list.json
      │  ├─ generation_manifest.json
      │  └─ …                         # 生成器保存的 profile、任务和场景
      ├─ plan.json                    # 全局编号、分片、配置和输入哈希
      ├─ plan.sha256
      ├─ controller.lock              # 总控制器的操作系统文件锁
      ├─ control.json                 # 全局预算、持久化完成序号、停止状态
      ├─ stop_report.json             # 仅停止时生成，含原因及收尾任务
      ├─ shards/
      │  ├─ shard_00/
      │  │  ├─ ledger.json
      │  │  ├─ writer.lock
      │  │  └─ attempts/
      │  │     └─ a000000/            # 全批次唯一 attempt 编号
      │  │        ├─ worker.log
      │  │        ├─ started.json     # 启动标记；锁释放后也禁止重复起飞
      │  │        ├─ run/
      │  │        │  ├─ attempt_ledger.json
      │  │        │  └─ attempts/<uuid>/<timestamp>/
      │  │        │     └─ …          # 独立 SITL 工作目录、参数、原始日志
      │  │        ├─ analysis/        # 选定正式分析及来源绑定
      │  │        └─ result.json      # 绑定输入及证据哈希的结果
      │  └─ shard_01/                 # 相同布局，独立端口与目录
      ├─ merged_records.json          # 按全局编号排序的任务结果
      ├─ analysis_selections.json
      ├─ audit_attempt_ledger.json
      ├─ dataset/                     # 全局编号顺序统一导出
      ├─ dataset_audit.json
      ├─ language/                    # 基于统一数据集生成描述
      └─ final_report.json
```

运行和分析的精确路径以 `result.json` 与台账为准。锁文件在进程退出后可以继续存在，锁是否占用由操作系统判定，不能用文件存在与否判断存活。控制器独占写入全局状态和各片台账；执行进程只写自己的 attempt 目录。完整结果先原子落盘，核验证据后才登记完成；恢复不会把跨文件写入假定为一个原子事务。

## 合并与提交检查

`finalize` 先检查任务无重复、无遗漏、无其他批次混入，正式分析及运行来源绑定完整，协议版本、质量策略和证据哈希一致，且所有执行进程已收尾。合并按原全局编号排序，随后统一导出、审计、生成描述及一致性检查、加载检查和汇总。失败/不合格记录保留，资格标记沿用现有规则。描述依据统一数据集清单生成，不能拼接各片独立描述。汇总继续列出巡逻阶段时序进度差的中位数、最大值和超限比例，未知单列，仅用于诊断。

CI 保留原有 141 项发布离线测试，并加入 `test_parallel_batch`、`test_parallel_worker`、`test_parallel_finalize`、`test_parallel_file_sizes`。大小检查为 **5 MiB = 5,242,880 字节**：仅检查本次相对基线新增、修改或重命名的 Git 文件对象，超过阈值即失败；未修改的历史大文件不会阻断新提交。它是 CI 门禁，不是本机 `git commit` 钩子。可在仓库根对已提交的变更手动检查：

```powershell
conda run -n $EnvName --no-capture-output python .github/scripts/check_file_sizes.py --base '<变更前提交>' --head HEAD
```

检查读取提交里的文件大小，即使工作区文件被缩小也不能绕过；临时 Git 仓库测试覆盖新增超限、边界值、旧文件不变/修改/删除/重命名等情况。GitHub Actions 只取必要的基线提交和浅层历史，不下载整个旧数据历史。实际离线测试结果、受限历史测试与提交号见暂停 1 报告。
